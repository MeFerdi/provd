---
title: Decision records
description: What Provd records for every check, and how to verify a record hasn't changed.
---

Every call to `POST /v1/actions/evaluate` writes a decision record: what you asked, which signals ran, what they found and what Provd recommended. The response carries the record's hash as `decision_record_hash`, so you can store it next to the trade in your own system.

When a dispute, an auditor or a regulator asks why a release went ahead, you can show the record and prove it is the one produced at the time.

## What's in a record

| Field | Contents |
|---|---|
| `intent_id` | Your reference for the trade. |
| `intent` | The intent as you sent it: chain, intent type, counterparty (wallet address, phone hash), rails, amounts, context. |
| `signals` | Each signal that ran, its value, its contribution to the score, the reason and source references. |
| `signal_coverage` | For each signal, whether it ran on `full`, `partial` or `none` of its data. |
| `decision` | Score, risk level, recommended action and flags. |
| `engine_version` | The scoring engine version that made the decision. |
| `created_at` | When the decision was made (UTC). |

Records hold hashed phone identifiers only, never raw numbers.

## Fetch a record

```bash
curl -s https://api.provd.tech/v1/decisions/order-48213 \
  -H "X-API-Key: $PROVD_API_KEY"
```

```json

  "intent_id": "order-48213",
  "record": { "intent_id": "order-48213", "intent": { "…": "…" }, "signals": [], "signal_coverage": {}, "decision": {}, "engine_version": "2026.10.0", "created_at": "2026-10-03T13:11:16.891600+00:00" },
  "record_hash": "7eb6c86d3878be10e32acfe84a9ce9f0d923c75f67be6e839b173112c91164a5",
  "hash_algorithm": "sha256 over canonical JSON (sorted keys, no whitespace)",
  "signature": { "algorithm": "ecdsa-secp256k1-sha256", "key_id": "f0f85b25dd51b813", "public_key": "02…", "value": "…128 hex…" },
  "merkle": { "leaf_index": 0, "proof": [{ "side": "right", "hash": "…" }], "root": "26c31c7e…", "algorithm": "…" },
  "batch": { "batch_id": "e0a03a1e-…", "merkle_root": "26c31c7e…", "leaf_count": 2, "sealed_at": "…",
             "anchor": { "method": "opentimestamps", "status": "anchored", "reference": "bitcoin:block:…", "proof_url": "/v1/proof/batches/e0a03a1e-…/ots" } },
  "proof_status": "anchored"

```

You can only fetch decisions made with your own keys.

## How the proof works

1. **Hash.** The record is serialized as canonical JSON (keys sorted, no whitespace, UTF-8) and hashed with SHA-256. That is `decision_record_hash`, returned the moment you call evaluate.
2. **Signature.** Provd signs the hash with a dedicated secp256k1 key (compact `r‖s`, low-S). The public key is published at `GET /v1/proof/keys`; pin it in your system.
3. **Batch.** Every few minutes, new decisions are sealed into a Merkle tree (`leaf = SHA256(0x00‖hash)`, `node = SHA256(0x01‖left‖right)`, odd node promoted). Your record gets an inclusion proof against the batch root.
4. **Anchor.** The batch root is timestamped on **Bitcoin through OpenTimestamps**. The proof is `pending` straight away and becomes `anchored` once the calendar's Bitcoin transaction confirms, usually within a few hours. Nobody, including Provd, can later change a record without breaking this chain.

`proof_status` tells you where a record is: `signed: joins the next batch within minutes` → `anchoring` → `anchored`.

## Verify a record yourself

The quickest way is in the browser: paste the JSON into [Verify a decision](/verify). It recomputes the hash, checks the signature and folds the Merkle proof on your device; nothing is sent to Provd.

For scripts and CI, download the verifier ([verify_decision.py](/tools/verify_decision.py)) and run it on a saved decision:

```bash
curl -s https://api.provd.tech/v1/decisions/order-48213 -H "X-API-Key: $PROVD_API_KEY" > decision.json
pip install cryptography
python verify_decision.py decision.json --public-key <public_key from /v1/proof/keys>
```

```
[ok] record hash 7eb6c86d…
[ok] signature by key f0f85b25dd51b813
[ok] merkle inclusion, leaf 0 -> root 26c31c7e…
[..] anchor: opentimestamps anchored bitcoin:block:…
```

It exits non-zero if anything fails. Change one field in the record and the hash and signature checks fail.

To check the anchor independently, download the batch proof and use the official OpenTimestamps client:

```bash
curl -s -o batch.ots https://api.provd.tech/v1/proof/batches/<batch_id>/ots
pip install opentimestamps-client
ots verify -d <merkle root> batch.ots
```

### Just the hash, in a few lines

```python
import hashlib, json
canonical = json.dumps(resp["record"], sort_keys=True, separators=(",", ":"), ensure_ascii=False)
assert hashlib.sha256(canonical.encode("utf-8")).hexdigest() == resp["record_hash"]
```

Use a JSON serializer that keeps numbers exactly as received. Some languages rewrite numbers such as `1.0` as `1`, which changes the hash.
